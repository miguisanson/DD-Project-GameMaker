1. WHAT GAME THIS IS
--------------------
This is a GameMaker Studio 2 pixel-art dungeon RPG with a Game Boy-like presentation.

Core identity:
- low internal resolution: 160x144
- integer-style scaling and handheld-aware fit-to-screen behavior
- 16x16 tile/grid overworld movement
- room-to-room dungeon crawling
- overworld enemies that chase the player and collide into battle
- 1v1 turn-based battles in rm_battle
- cutscenes + dialogue + typewriter text
- inventory, consumables, equipment, skillbooks, and loot
- save/load slots
- custom modal popup UI with dimming and fade-in/fade-out

Narrative/gameplay framing:
- The player begins as a porter / Nobody who falls into a surreal underground place.
- The player does not choose a real class at the title screen.
- The player later chooses Knight / Archer / Mage via a class chest in rm_floor1.
- The campaign is effectively a compact level 1-10 RPG, not a long-form 1-99 RPG.

Project direction:
- Systems are intended to stay data-driven.
- Recent work consistently pushed logic into centralized helpers rather than room-by-room hacks.
- The repo still contains some legacy assumptions and older docs; code is the final authority.


2. HIGH-LEVEL ROOM / FLOW STRUCTURE
-----------------------------------
Main rooms:
- rm_start: title/main menu
- rm_cutscene: centralized cutscene room
- rm_floor1 through late floors: overworld dungeon rooms
- rm_battle: battle room

Current player-facing flow:
- Title -> New Game
- Title opens difficulty popup
- Difficulty confirm -> intro cutscene through rm_cutscene
- Intro finishes -> rm_floor1
- Player starts as Nobody
- Player interacts with class chest in rm_floor1
- Class selection popup opens
- Class applies during black flash transition
- Gameplay continues normally

Load flow:
- Title -> Load Game
- Load popup -> slot confirm -> save snapshot is applied
- Exact saved room/x/y/face are restored
- Load uses a slower loading-style black transition so the loaded room stays hidden
- Title dim is intentionally held through the handoff so brightness does not flicker while leaving the menu

Ending flow:
- Late-game transition from rm_floor9_5 routes to rm_cutscene with cutscene id ending
- Ending plays as multi-segment cutscene definitions
- Final return goes back to rm_start

Death flow:
- Player HP <= 0 triggers the game_over cutscene in rm_cutscene
- After the game_over cutscene, the game tries to load the current/latest save slot
- If no save exists, it returns to rm_start

Battle flow:
- Overworld enemy collision can either auto-resolve or transition into rm_battle
- rm_battle resolves a 1v1 fight
- On victory: EXP + loot + post-battle dialogue handoff back to overworld
- On defeat: game_over cutscene flow
- On run: return to overworld through transition system

5. DIFFICULTY POPUP ARCHITECTURE
--------------------------------
The difficulty popup is a title-only popup, not part of the regular in-game UI controller stack.
That is an important special case.

Where it lives:
- input/state: objects/obj_start_controller/Step_0.gml
- draw: objects/obj_start_controller/Draw_64.gml

Important details:
- New Game opens the difficulty popup by calling UI_ModalRootBegin("title_difficulty").
- Confirming a difficulty calls UI_ModalRootHold("title_room_change").
- When the difficulty popup closes into the intro flow, gs.in_main_menu is set false before leaving the title.
- This prevents main menu buttons from reappearing during the transition.

Why it is special:
- Shared modal dim still tracks title difficulty through UI_GetModalVisualAlpha(), which looks at obj_start_controller.
- But obj_ui_controller/Draw_64.gml explicitly skips drawing shared modal dim while title difficulty is active.
- obj_start_controller/Draw_64.gml draws the difficulty popup's local dim behind the popup.
- This is intentional so the popup box is not over-dimmed.

If another agent tries to "unify" this without reworking draw ownership, the dim will likely end up on top of the difficulty box again.


6. POPUP / MODAL / DIM SYSTEM
-----------------------------
The current popup dim architecture is centralized.
This is important because it was reworked specifically to avoid flicker between linked popups.

Primary helpers:
- UI_PopupFadeAlpha
- UI_PopupAlpha
- UI_ModalRootEnsure
- UI_ModalRootBegin
- UI_ModalRootTransfer
- UI_ModalRootHold
- UI_ModalRootEnd
- UI_GetModalVisualAlpha
- UI_UpdateModalDimState
- UI_DrawModalDim

Where they live:
- scripts/scr_player/scr_player.gml

How the system works now:
- A modal root owns the dim, not each popup individually.
- Linked popup chains transfer or hold the modal root instead of dropping to no owner.
- This is how the project avoids dim flicker between:
  - Bed -> Rest -> Save Game
  - Load popup -> load transition into gameplay
  - Difficulty popup -> cutscene/game start handoff

Current hold modes:
- transition
- gameplay_load
- title_room_change

Current popup fade rule:
- Popup content alpha is meant to follow popup box alpha.
- Shared dim alpha is derived from the active popup visual alpha where possible.
- The intended result is that popup and dim fade in/out together.

Special caveat:
- Title difficulty popup is still a special-case draw owner as described above.

If another agent adds a new modal/popup and hardcodes its own dim rectangle, they will probably reintroduce flicker or inconsistent layering.
The preferred pattern is:
- begin modal root
- transfer modal root across linked popups
- use shared dim unless the popup is a deliberate title-special-case like difficulty

Current exact per-level rule:
- Every level-up gives exactly 1 manual stat point.
- Every level-up also gives exactly 1 automatic class stat increase.
- Auto stat mapping comes from the class DB through auto_stat.
- Nobody has no auto-stat fallback; LevelUp_AutoStatForClass returns -1 for Nobody.

Current EXP table:
- 1 -> 2 = 15
- 2 -> 3 = 30
- 3 -> 4 = 50
- 4 -> 5 = 75
- 5 -> 6 = 105
- 6 -> 7 = 140
- 7 -> 8 = 180
- 8 -> 9 = 225
- 9 -> 10 = 275
- beyond 10: 0, because cap

Current resource recompute behavior:
- RecomputeResources in scripts/scr_stats/scr_stats.gml
- HP grows mainly from class/base level growth
- DEF adds only a small weighted HP bonus through PLAYER_HP_DEF_BONUS_FACTOR
- MP grows from class/base level growth plus INT weighting
- Manual DEF/INT allocation no longer causes the previous large runaway retroactive HP/MP behavior

Current level-up heal behavior:
- Level-up does not fully heal the player.
- Instead, HP and MP increase only by the amount of new max HP / max MP gained from that level.
- This preserves prior damage instead of resetting the player to full.

Manual stat allocation:
- Stats tab inside the menu allows spending unspent stat_points on STR/AGI/DEF/INT/LUCK.
- Pending allocation can be confirmed or canceled.
- Agents should inspect Menu_StatsSync / Menu_StatsApply / Menu_StatsDiscard in scripts/scr_menu/scr_menu.gml before changing stat UI.

- obj_game_controller/Step_0.gml applies load_spawn_pending after room entry so saved coordinates beat the default room spawn

Bed flow:
- interacting with a bed opens Bed menu, not Save menu directly
- Bed menu options are Rest and Back
- Rest opens Save Game menu
- Saving from a bed fully heals HP and MP before the save write
- After save write, the save flow reloads the selected slot and then shows Game saved.

Enemy respawn on save:
- Saving resets normal enemies via enemy_reset_version logic
- Mini boss and final boss are intentionally not treated like regular respawning enemies

Load popup behavior:
- if no save exists, Load Game should effectively close back out rather than leaving broken state
- there is message handling around no-save conditions in the save menu flow

If another agent changes debug/UI, they should inspect:
- scripts/scr_debug.gml
- objects/obj_sfx_manager/Draw_64.gml


20. KNOWN FRAGILE AREAS / THINGS EASY TO BREAK
----------------------------------------------
1. Title load transition and dim handoff.
   - Main menu load is special.
   - The dim must remain sustained while leaving the title.
   - Main menu buttons must not flash back in.
   - The title background should not do a separate alpha fade.

2. Title difficulty popup layering.
   - It is a title-special-case popup.
   - Shared dim logic sees it, but the local dim for drawing is still owned by obj_start_controller.

3. Popup dim ownership.
   - Do not reintroduce per-popup hardcoded dim rectangles unless you are deliberately replacing the modal-root system.
   - Linked popup chains are supposed to transfer/hold the modal root.

4. Save/load exact position restore.
   - The load flow deliberately overrides normal spawn behavior with load_spawn_pending.
   - If a future change causes the player to spawn at room start instead of saved coordinates, inspect obj_game_controller/Step_0.gml and Save_ApplySnapshot.

5. rm_cutscene player visibility.
   - rm_cutscene should never show the player.
   - obj_game_controller has a safety destroy for stray obj_player there.

6. Class application timing.
   - Class changes are intentionally hidden under black flash transition.
   - Do not reapply class sprites visibly before the black screen if the intent is to hide the swap.

7. Status icon assumptions.
   - The DB still contains icon fields for many statuses.
   - Enemy battle draw intentionally overrides non-core icon presentation with text-sign fallback.

8. Battle log/reward duplication.
   - This project already had redundancy cleaned out.
   - Timed attack feedback and reward messaging should not be duplicated across multiple UI channels unless deliberate.

9. Grid alignment after transitions or auto-resolve.
   - Recovery helpers exist for a reason.
   - If another agent bypasses them, the player may feel offset or semi-stuck until moving once.

10. settings_config.json authority.
   - Settings should not be silently restored from save slots again.

22. FINAL TAKEAWAY FOR ANOTHER AGENT
------------------------------------
This project is in a workable state, but several systems are deliberately centralized because they were previously broken by local fixes.

The main places where a new agent can accidentally regress the game are:
- title menu load/dim/transition behavior
- popup dim ownership and linked-popup handoffs
- exact save-load position restore
- cutscene room ownership
- battle reward text duplication
- enemy status fallback presentation

If a change touches any of these, re-test them immediately in-engine.

If this file conflicts with code, trust code first and update this handoff file afterward.
